# Engineering Principles & Decision Log

> **Що це:** жива пам'ять проєкту. Тут — _чому_ ми робимо так, а не інакше.
> `CLAUDE.md` каже **що** робити (короткі правила). Цей файл каже **чому** (розгорнуто + історія рішень).
> Коли впираємось у нетривіальний вибір і вирішуємо його — записуємо сюди новий запис у «Decision Log», щоб не переспорювати вдруге.

## Частина 1. Незмінні принципи

### Архітектура шарів

- **Напрям залежностей один:** `route → service → repository → DB`. Ніколи навпаки.
- **Кожен шар має одну причину знати те, що знає:**
  - route — про HTTP (статуси, заголовки, `request.user`);
  - service — про бізнес-правила (домен), і **нічого** про Fastify чи Prisma;
  - repository — про сховище (Prisma/SQL), і **нічого** про HTTP.
- **Лакмус:** чи можу я викликати `service.method()` у юніт-тесті без підняття HTTP і без реальної БД (з мок-репозиторієм)? Якщо так — межі правильні.
- **Навіщо це коштує зусиль:** у Таску 2 (Postgres/Prisma → Mongo/Mongoose) переписуємо **лише `*.repository.ts`**. Service, route, схеми — не чіпаємо. Це головна віддача від шарів.

### Помилки як значення

- Доменні помилки — це класи (`AppError` → `NotFoundError`, `ConflictError`, ...) зі `statusCode` + `code`. Кидаємо їх у service/repository.
- HTTP-код призначає **одне** місце — центральний `setErrorHandler`. У хендлерах роутів **не** пишемо `reply.status(4xx)`.
- Єдиний конверт помилки: `{ error: { code, message, details? } }`. Stack — лише в лог, ніколи в тіло відповіді (OWASP-гігієна).
- Нічого не «ковтаємо» мовчки: або обробили усвідомлено, або `throw` далі.

### Типи

- **DRY з головою:** дедуплікуємо _знання_, а не _схожість_. Два типи, що виглядають однаково, але змінюються з різних причин, — лишаються окремими.
- API-контракт (`*Body`, `z.infer`) і модель запису в БД (`*.types.ts`) — різні речі, навіть коли схожі.
- Зовнішні дані (API, env, черги) валідуємо на межі через Zod; типи виводимо з `z.infer`.
- `as` — тільки на валідованій межі (напр. звуження `unknown` у error-handler). Глибше в коді `as` = запах.

### Простота (KISS / YAGNI)

- Не додаємо абстракцію під уявне майбутнє. **Rule of three:** узагальнюємо на третьому реальному випадку, не на першому.
- «Мінімальна зміна» — це добре. Простий зрозумілий код > «розумний».
- Знати, коли НЕ додавати шар, — складніше й цінніше, ніж додати.

### Безпека (звички за замовчуванням)

- `userId` для запису беремо **лише** з довіреного JWT (`request.user.id`), ніколи з тіла запиту (інакше IDOR).
- На кожному ресурсі перевіряємо власність (`where: { id, userId }`), а не лише існування — щоб не редагувати/бачити чуже.
- Однакове повідомлення на «нема юзера» і «невірний пароль» (проти user enumeration).
- Конфіг валідуємо на старті, крашимось при відсутньому секреті (жодних дефолтів типу `|| 'secret'`).

## Частина 2. Decision Log

Формат запису: **Контекст → Рішення → Чому → (Trade-off)**.

### 2026-07-18 · Валідація env на старті (fail-fast)

- **Контекст:** секрети/URL були розкидані як `process.env.X || 'default'`.
- **Рішення:** `config/env.ts` — Zod-схема парсить `process.env`, при помилці `process.exit(1)`.
- **Чому:** сервіс або стартує зі здоровою конфігурацією, або не стартує взагалі. `JWT_SECRET || 'secret'` — це тиха діра в безпеці.

### 2026-07-18 · Рефактор роутів у service + repository

- **Контекст:** логіка (Prisma, try/catch) жила прямо в роутах → не тестується, дублюється.
- **Рішення:** `route → service → repository`. Роут тонкий; service — бізнес без req/reply; repository — єдине місце з Prisma.
- **Чому:** тестованість + декаплінг від БД (готовність до Mongo у Таску 2).

### 2026-07-18 · `instanceof` лише проти рантайм-класу

- **Контекст:** хотіли `error instanceof FastifyError` в error-handler.
- **Рішення:** для `FastifyError` — **ні** (це лише TS-інтерфейс, немає рантайм-класу) → звужуємо приведенням `as FastifyError` на межі. Для `Prisma.PrismaClientKnownRequestError` — **так** (це реальний експортований клас).
- **Чому:** `instanceof` вимагає праворуч значення-конструктор. Тип-інтерфейс ним не є.

### 2026-07-18 · Часткове оновлення: `!== undefined`, не truthy

- **Контекст:** будували patch через `input.x && { x }`.
- **Рішення:** тільки `if (input.x !== undefined)`.
- **Чому:** truthy-перевірка мовчки викидає валідні `''` / `null` / `0`. `undefined` = «не передали», будь-яке інше значення = «застосувати» (включно з очищенням у `null`).
- **Бонус:** помітили заодно мертвий `?? null` після гарду `!== undefined` — прибрали. Читай типи.

### 2026-07-18 · Де перекладати помилку БД (P2002)

- **Контекст:** дублікат email → треба 409. Спершу поклали переклад у service (знав про Prisma), потім винесли повний ACL (репо → нейтральна `UniqueConstraintError` → service → `ConflictError`).
- **Рішення:** **репозиторій** ловить `P2002` і кидає одразу доменну `ConflictError`. Нейтральний проміжний клас **не** вводимо.
- **Чому:** знання про `P2002` = територія репо (жорстке правило дотримано: Prisma лише в репо). А окремий нейтральний шар заради **одного** випадку — передчасна абстракція (порушує KISS/YAGNI). Введемо на 3-му випадку (rule of three).
- **Trade-off:** репо кидає доменну `ConflictError` (легка зв'язність із доменом). Свідомо приймаємо заради простоти; розділимо, коли реально припече.

### 2026-07-18 · `buildApp()` окремо від `listen`

- **Контекст:** усе жило в `server.ts`, тестувати неможливо.
- **Рішення:** `app.ts` збирає інстанс і повертає його; `server.ts` лише `listen` + graceful shutdown.
- **Чому:** відкриває тести через `app.inject()` без реального порту (Фаза 7). `server.ts` відповідає лише за життєвий цикл процесу.

### 2026-07-18 · Fastify: `decorate` на корені vs `fastify-plugin`

- **Контекст:** виносили `authenticate` із server.ts у плагін.
- **Рішення:** `registerAuth(app)` викликаємо прямо на кореневому інстансі (не через `app.register`).
- **Чому:** плагіни Fastify інкапсульовані — декоратор, доданий усередині `register`, не «протікає» назовні. Глобальний декоратор ставимо на корінь (або обгортаємо в `fastify-plugin`, але тоді потрібна залежність).

### 2026-08-06 · Мультитенантність: expand → backfill → contract

- **Контекст:** `Task.userId` → `Task.projectId`, а в таблиці вже були дані. `migrate dev` відмовився додавати NOT NULL колонку.
- **Рішення:** три окремі міграції + одноразовий скрипт: `projectId String?` → `prisma/backfill.ts` (Workspace `Personal` + Membership OWNER + Project `Default` у транзакції на юзера) → `SET NOT NULL`.
- **Чому:** між кроками БД завжди в робочому стані — це і є zero-downtime. Схема і дані рухаються разом; забіжиш схемою вперед — клієнт більше не вміє писати `null`, хоча NULL-и в БД ще лежать.
- **Trade-off:** три міграції замість однієї. Приймаємо — на проді альтернативи немає.
- **Правило:** бекфіл-скрипти **не видаляємо**. Це документ «як переводили дані» + його ще запускати на проді.

### 2026-08-06 · Реляційний бекфіл — TS-скрипт, не SQL у міграції

- **Контекст:** бекфіл створює ланцюг Workspace→Membership→Project→Task з uuid-звʼязками.
- **Рішення:** окремий `prisma/backfill.ts` (`npx tsx`), кожен юзер — в інтерактивній транзакції; ідемпотентний через фільтр `projectId: null`.
- **Чому:** простий бекфіл (одна колонка) — SQL у міграції; **реляційний** — app-скрипт, інакше пекло з CTE/`RETURNING`. Ідемпотентність обовʼязкова: скрипт може впасти на 50-му з 200.
- **Деталь:** усередині `$transaction` — тільки `tx`, ніколи `prisma` (інакше запис піде повз транзакцію).

### 2026-08-06 · Soft delete: каскад руками, slug звільняємо в коді

- **Контекст:** `deletedAt DateTime?` на Task/Project/Workspace.
- **Рішення:** (1) каскад soft-delete робимо явно в транзакції, не покладаючись на `onDelete: Cascade`; (2) при soft delete перейменовуємо slug (`${slug}-deleted-${Date.now()}`); (3) `onDelete: Cascade` у схемі лишається — для permanent delete.
- **Чому:** `Cascade` — правило БД на фізичний `DELETE`, на `UPDATE deletedAt` воно не спрацьовує. Читань більше, ніж видалень → оптимізуємо частий шлях (фільтр `deletedAt: null` замість join'а до предків).
- **Чому не partial unique index (`WHERE deletedAt IS NULL`):** Prisma не вміє його описати. Спроба протягнути сирим SQL дала failed-міграцію + вічний drift (Prisma дропала б невідомий їй індекс). **Правило:** якщо ORM не описує конструкцію — вирішуй на рівні коду, а не напівзаходом у міграції.
- **Дисципліна:** фільтр `deletedAt: null` живе **тільки в репозиторії** — єдиному шарі з Prisma.

### 2026-08-06 · RBAC: ієрархічний ранг ролей

- **Рішення:** `OWNER 4 > ADMIN 3 > MANAGER 2 > MEMBER 1`. Permanent delete воркспейсу — OWNER; зміна ролей — ADMIN+; кік + CRUD проєктів — MANAGER+; CRUD тасок — MEMBER+.
- **Чому ранг, а не набір permissions:** матриця виявилась суцільно вкладеною (кожна дія = префікс зліва, без дірок) → числове порівняння достатнє. KISS.
- **Тригер переходу на permissions:** поява ролі, що випадає з ієрархії (напр. `BILLING` — платить, але не чіпає проєкти).
- **Інваріанти:** не можна кікнути/змінити того, чий ранг ≥ твого; останнього OWNER не можна ні кікнути, ні понизити.

### 2026-08-06 · `Task.userId` = аудит, НЕ авторизація

- **Контекст:** після переходу на проєкти поле лишили («хто створив»).
- **Рішення:** авторизація **тільки** ланцюгом `task → project → workspace → membership`. `where: { userId }` для доступу — заборонено.
- **Чому:** поле виглядає знайомо з Фази 1, і рука тягнеться перевіряти доступ по ньому. Наслідки: колега по воркспейсу не побачить чужу таску (хоча має право), а вигнаний юзер далі дістане свої старі.

### 2026-07-18 · Логи в cron — інжектимо логер

- **Контекст:** хотіли `fastify.log` у `cron.ts`, там немає інстансу.
- **Рішення:** `initScheduler(log)` приймає `FastifyBaseLogger`; викликаємо `initScheduler(app.log)` у `server.ts`.
- **Чому:** cron працює поза request-скоупом — немає `request.log`. Передаємо app-рівневий логер. Пишемо структуровано: `log.warn({ поля }, 'message')`.
